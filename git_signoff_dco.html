Git · DCO · commit metadata

一行 signoff
到底承諾了什麼？

把 Signed-off-by 放進 commit，不是在替程式碼加密，也不是在取代 review。它是在一條可追溯的責任鏈上，留下提交者依專案規範作出的聲明。

中心問題：誰為何種聲明留下了什麼證據？
commit 9c0ffeemain

docs: clarify installation steps

Signed-off-by: Lin Example <lin@example.com>
這一行是 Git trailer；其實際法律／流程意義取決於專案採用的 DCO 與政策文字。
責任鏈metadata 控制台不要混在一起實作與收尾
先看路徑，再看名詞

一筆變更如何走過責任鏈？

這不是所有專案唯一的流程，但能把每一種 metadata 放在正確的位置。

01 修改者完成或參與變更的人
02 提交者建立 commit、可加 signoff
03 DCO 檢查專案可要求 trailer
04 審閱者檢查內容與風險
05 維護者依政策決定是否合併
先懂這個：signoff 的重點是「提交者的聲明」；它不會自動證明程式正確、沒有漏洞，或每位原作者都已被辨識。那些問題要靠測試、審閱、授權流程與專案治理共同處理。
可點選的 commit 解剖圖

切換 metadata，看看它能說什麼

Author

Git 的作者欄描述誰被記為原始變更的作者；它是歷史 metadata，不是對授權、review 或加密完整性的萬用證明。

回答：這筆變更的作者記錄是誰？

不回答：是否已符合 DCO、是否被審閱、是否做了加密驗證。

五個看起來相近、實際問題不同的記號

記號它主要回答它不等於怎麼看
Author誰被記為原始作者已獲 DCO 同意或已審閱commit header
Committer誰建立／套用這筆 commit唯一的程式作者commit header
Signed-off-by提交者依專案 DCO／政策所作的聲明加密簽章、code reviewcommit trailer
Reviewed-by有人針對變更表示已審閱承擔 DCO 聲明、測試必然通過review trailer／PR 流程
GPG／SSH signature可驗證某把金鑰對 commit／tag 的簽署自動取得 DCO、完成審閱Git signature verification
常見誤解：git commit -s 的 -s 是加入 signoff trailer；它不是 git commit -S 的加密簽章。小寫與大寫的差別，剛好反映兩種不同問題。
最小實作

先讀專案規範，再留下正確的紀錄

步驟 1 · 找政策

確認此專案是否採 DCO

閱讀 CONTRIBUTING、提交指南與 CI 訊息。DCO 的文字與例外規則由專案維護者定義，不要只因看過某個 trailer 就自行推定。

步驟 2 · 建立 signoff

讓 Git 在 commit 尾端加一行

git commit -s -m "docs: clarify setup"
# 為既有 commit 補上：
git commit --amend -s --no-edit
步驟 3 · 檢查內容

確認身分與 trailer

確認 Git 設定的姓名／email 合適，再用 git log -1 --format=full 或專案工具檢查 trailer 是否出現。不要偽造他人的姓名或 email。

步驟 4 · 仍要完成工程工作

signoff 後還有測試與 review

跑測試、回答審閱意見、確認授權與貢獻政策；signoff 是責任鏈上的一站，不是合併通行證。

帶走這個比喻：把 commit 想成一份交接單。Author、Committer、signoff、review 與加密簽章像不同欄位；每一欄都重要，但不能拿其中一欄假裝整張表已填完。

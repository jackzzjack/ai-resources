BASH · PROCESS CONTROL

coproc：可對話的背景程序

把長時間執行的命令放到背景，還能透過雙向管線持續傳送工作與接收結果；這就是 Bash 的協同程序（coprocess）。

定義運作流程程式範例常見陷阱如何驗證

先抓住心智模型：背景工作者 + 兩條管線

一般背景命令

command & 讓命令在背景跑，但父 shell 通常不會再與它持續對話。

coproc

Bash 在背景啟動命令，並建立一條「送入」管線與一條「讀回」管線。

適合什麼情況？

重複交給同一個程式處理資料、想避免每筆工作都重新啟動程序時特別有用。

不是執行緒

它是另一個 OS 程序；共享的是檔案描述元與管線，不是 Bash 變數記憶體。

一句話：coproc 是 Bash 提供的「可寫入、也可讀取」背景子程序介面。它是 Bash 功能，請用 bash script.sh，不要預設由 sh 執行。

資料怎麼走？

01 STARTcoproc WORKER { ...; }
建立背景子程序並記下 PID。
02 WRITEprintf ... >&"${WORKER[1]}"
父 shell 從寫入端把資料交給工作者。
03 PROCESS工作者從標準輸入讀資料、計算，再輸出結果。
04 READ + WAITread ... <&"${WORKER[0]}"
父 shell 接收結果，最後以 wait 收尾。
# 命名協同程序時，Bash 會建立陣列 WORKER： WORKER[0] # 讀取工作者 stdout 的檔案描述元 WORKER[1] # 寫入工作者 stdin 的檔案描述元 WORKER_PID # 工作者的 PID（可用 wait 等待）

可執行範例：把數字交給背景工作者平方

工作者逐行讀數字、算平方並回傳；父 shell 傳入兩筆資料，再讀取兩筆結果。

#!/usr/bin/env bash set -euo pipefail coproc SQUARE { while IFS= read -r number; do printf '%s\n' "$((number * number))" done } # 傳兩筆工作；[1] 是通往工作者 stdin 的寫入端 printf '%s\n' 7 12 >&"${SQUARE[1]}" # [0] 是從工作者 stdout 讀回的讀取端 read -r first <&"${SQUARE[0]}" read -r second <&"${SQUARE[0]}" printf '結果：%s、%s\n' "$first" "$second" # 關閉輸入，讓 while 讀到 EOF 後結束，再回收子程序 exec {SQUARE[1]}>&- wait "$SQUARE_PID"

互動輸出預覽

此處模擬範例的輸出順序；實際驗證請依下一節執行腳本。

$ bash coproc-demo.sh
緩衝提醒：若工作者是 Python、grep 或其他程式，輸出可能被緩衝，讓讀取端看似卡住。可改為讓工作者每次輸出後 flush，或在適當情境使用其 line-buffered / unbuffered 選項。

常見陷阱與改法

現象原因建議
sh script.sh 報語法錯coproc 與陣列檔案描述元是 Bash 特性。使用 shebang #!/usr/bin/env bash，並以 bash script.sh 執行。
read 一直等待工作者尚未輸出、輸出被緩衝，或雙方都在等對方。設計明確的每筆請求／每筆回應協定；必要時使用 read -t 5 設逾時。
工作者永遠不結束寫入端仍開著，工作者的 read 還沒看到 EOF。送完資料後關閉寫入端，再 wait "$NAME_PID"。
變數沒有被子程序更新協同程序是子程序，變數空間與父 shell 分離。把結果寫到 stdout，父 shell 再用 read 接收。
只需要一筆輸入就用了 coproc建立與同步成本不一定划算。單次工作優先考慮命令替換、管線或一般背景命令。

驗證方式：確認資料真的往返、程序真的結束

□ 將範例存成 coproc-demo.sh，執行 bash -n coproc-demo.sh 檢查語法。
□ 執行 bash coproc-demo.sh；預期看到 結果：49、144。
□ 暫時加入 echo "$SQUARE_PID"，用 ps -p PID 觀察背景程序。
□ 測試異常輸入與逾時；確認腳本不會無限制卡住，且能清楚回報失敗。
何時該用？當你要長時間保留一個互動式命令、持續交辦多筆工作，又能定義清楚的輸入／輸出界線時，coproc 是實用工具；否則，較簡單的 pipe 或函式通常更容易維護。

一眼看懂：終端機不是多一條裝飾列

狀態列將工作階段中原本分散的訊號濃縮成一眼可讀的儀表板；它不會替你完成工作，也不是 AI 模型本身。

先懂這個：先確認 CLI 是否支援自訂狀態列與目前版本需求；畫面顯示的專案路徑、分支、token 或活動紀錄，仍是你的工作資訊，應先理解它在本機如何被讀取或保存。

三個工具，三種接線位置

Claude Code

ccstatusline

面向 Claude Code 的可客製狀態列思路；適合想把模型、Git 分支、用量或其他工作訊號安排到固定視線位置的人。

Copilot CLI

copilot-hud

面向 GitHub Copilot CLI 的 HUD 形式；可把專案、分支、上下文與工具活動視為同一個工作面板的訊號。

Copilot CLI

copilotstatusline

以狀態資料與可執行命令為核心的路徑；適合希望調整呈現方式、理解本機用量歷史與互動設定的人。

訊號旅程：從 CLI 事件到你的一瞥

同一條狀態列可能同時接到多種訊號；這張圖提醒你分開思考「來源」、「轉譯」與「顯示」。

01 · 工作階段

CLI 的專案、對話、工具執行與環境狀態持續變化。

02 · 可用訊號

分支、路徑、模型、上下文或用量等資料依工具能力被提供。

03 · 狀態列設定

工具讀取可用資料，決定格式、更新節奏與是否記錄本機歷史。

04 · 人的判斷

你用一眼的提示決定是否查看差異、停止背景工作或回到任務。

常見誤解：狀態列的資訊密度愈高不一定愈好。若它讓你反覆追逐數字，應先減少訊號，而不是再加一個小工具。
